Lesson 1 · Layered Architecture Judgment

先分层，再选型

你不是要为整个文档系统选出一个“万能框架”。这节课会用一次 API 变更，带你判断门户、REST Reference、多 SDK Reference 和质量治理分别需要做什么决定。

建议用时 45–60 分钟 前置：已通过 Lesson 0 产出：你的分层架构决策
这节课的一个胜利

完成后，你看到 Docusaurus、OpenAPI、Sphinx 或 TypeDoc 时，不会急着给它们排总名次，而会先指出：它主要解决哪一层的问题，事实从哪里来，代价落在谁身上。

从一次真实形态的变更开始

假设一个合成的向量检索服务要给“创建 collection”能力新增一致性级别。REST 和四种 SDK 都计划在下一版本提供这项能力：

Surface可能的公开表达首先要核对的事实
RESTconsistencyLevel request fieldschema、允许值、默认值、错误响应
Pythonconsistency_level: ConsistencyLevel签名、类型、docstring、版本
Java.consistencyLevel(...)公开方法、类型、Javadoc、版本
GoConsistencyLevel option导出字段、类型、doc comment、版本
Node.jsconsistencyLevel?: ConsistencyLevel公开声明、类型、注释、版本

这些名字只是练习输入，并不代表 Milvus 当前生产 API。真正工作时，你必须回到各公开仓库验证。

先想 20 秒：只改 Docusaurus 页面会怎样？

页面可能描述了新参数，但接口契约或某些 SDK 根本没有发布；也可能源码已经支持，生成页面和导航却没有更新。门户能统一入口，却不能自动成为五套技术事实的所有者。

一个变更要经过四层

01 · PORTAL

文档门户

把教程、How-to、概念和各类 Reference 组织为一个读者体验。

02 · REST

接口契约

OpenAPI 描述 REST 接口可观察到的路径、参数、schema 和响应。

03 · SDK

源码提取

每种语言从自己的公开声明、类型和注释生成 SDK Reference。

04 · GOVERN

质量治理

CI、版本矩阵和人工评审共同发现缺页、错误版本和语义漂移。

必须记住的区别

统一读者入口解决“用户去哪里找”；统一事实来源解决“某项事实在哪里首先成立”。多 SDK 系统通常需要前者，但不应假装所有语言共享同一个源码事实。

点击一层，观察它的输入和失败点

门户层：统一体验，不重写全部事实

输入手写任务内容、导航配置、各 Reference 输出地址
→
输出统一导航、搜索、版本入口和发布站点

常见失败：生成成功但没有入口；旧版本链接到新 Reference；门户插件让事实来源变得不可追踪。

REST 层：契约先成立，再生成展示

输入OpenAPI 中的 path、operation、parameter、schema、response
→
输出经校验的 REST Reference，以及可选的 Mock、测试或客户端输入

Mock 是什么？它是按照契约返回预设响应的模拟服务，让前端或文档示例在真实后端尚未就绪时也能对接；它不等于真实业务实现。

SDK 层：每种语言保留自己的事实边界

输入Python/Java/Go/Node.js 的公开签名、类型、注释和导出
→
输出语言惯用、与对应 SDK 版本一致的 Reference

常见失败：为了页面整齐而手抄签名；生成器读取了错误分支；把语言惯用差异误判为能力不一致。

治理层：验证共同语义，不强迫共同拼写

输入版本矩阵、公开 surface 清单、质量规则和评审标准
→
输出CI 结果、缺口清单、发布门禁和需要人工判断的差异

常见失败：只检查页面是否存在，不检查默认值、允许值和版本；或要求所有语言使用相同参数名。

为什么原来的“框架总排名”让人难以理解

你看到的名称这节课主要把它放在哪一层正确的比较对象
Docusaurus / MkDocs / GitBook门户层其他门户方案的协作、构建、定制和生命周期代价
OpenAPI + rendererREST 层手写 REST Reference 或其他契约驱动管线
Sphinx/autodoc本课中的 Python SDK 层其他 Python 源码提取与 Reference 生成方式
Javadoc / Go doc / TypeDoc相应语言的 SDK 层同一种语言中的生成方式和维护约束
CI / 检查脚本 / 模板治理层不同风险对应的自动检查与人工评审方式

工具可以跨层，但决策必须先有主语。与其问“Docusaurus 和 Sphinx 谁更好”，不如分别问“门户如何发布”和“Python Reference 如何从源码提取”。

同层选择才有可解释的后果

门户：自主管理还是托管协作？

Docusaurus/MkDocs 更容易展示可重复的本地构建；GitBook 更突出托管协作与网页编辑。

展开看代价与反转条件

自主管理增加依赖升级和集成责任；托管方案增加平台边界与迁移问题。若非工程贡献者必须直接网页编辑，结论可能转向托管协作。

REST：手写还是 OpenAPI 驱动？

OpenAPI 驱动让参数和 schema 可校验、可派生；手写页面在叙述上更自由。

展开看代价与反转条件

OpenAPI 需要可靠契约和生成边界；手写需要人工同步。若 spec 并不代表真实接口，它就不能仅凭“可生成”成为可信来源。

SDK：手抄页面还是语言原生提取？

原生提取更容易追踪签名和类型；手写适合少量稳定 API 或解释性补充。

展开看代价与反转条件

原生工具链意味着多套环境和规则。若公开 surface 很小且长期稳定，建立完整生成管线的收益可能不足。

治理：统一拼写还是统一语义？

跨语言检查应比较能力、类型、默认值、允许值和版本，不应强迫相同命名风格。

展开看代价与反转条件

语义映射需要维护一份能力矩阵。只有当多 SDK 实际由同一 IDL 稳定生成时，才可能把更多一致性责任上移到共同生成源。

练习 A：把对象放回正确层次

为下面七项选择它们主要承担的层次。四个选项都使用相同长度的标签，避免视觉提示。提交后会立即看到解释；这只是练习反馈，不代表本课已经通过。

练习 B：写你的分层架构决策

不要先写工具总分。在聊天里用下面七行提交判断；可以写“缺少证据”，但要指出准备查什么。

1. 门户层：我会……，因为…… 2. REST 层：事实来源与生成边界是…… 3. Python 基线：我会从它验证…… 4. Java / Go / Node.js：我不会重建三套管线，而会先…… 5. 一个跨 SDK 漂移风险是…… 6. 对应的验证办法是…… 7. 如果……发生，我会重新评估上述选择。
提交前自检：不要偷换成“一个框架解决全部”
  • 你明确写出了门户、REST、SDK 和治理四层。
  • 门户负责统一体验，但不是所有 API 技术事实的所有者。
  • Python 是成熟基线，用来提出跨 SDK 检查问题，不是唯一要维护的 SDK。
  • 你的漂移风险包含可检查的事实，例如类型、默认值、允许值或版本。
  • 你的结论包含代价和反转条件，而不只是工具优点。

完成标准

练习 A 的即时反馈用于修正分层；真正通过需要你提交练习 B，并能在追问中解释四层、Python 基线的作用、一个跨 SDK 漂移风险及其验证方法。通过后，我会把你的判断整理成 ADR 草稿；你通过确认、纠正或拒绝其中的决定完成共同审阅。

如果你不知道某个工具属于哪一层，或者不知道实际 Milvus 仓库使用什么生成器，请直接问我。写“缺少证据”比根据工具名称猜测更专业。
