Lesson 0 · Orientation

先看懂系统，再修改系统

这节课只有一个目标：你能分清“事实来源、发布界面、工程决策、自动化命令”分别住在哪里。高级 technical writer 的工程感，往往就从这种边界意识开始。

建议用时 15–20 分钟 不改代码 产出：3 条自己的解释
和你的目标有什么关系？

面试官不只关心“页面写得怎么样”，还会追问：事实从哪里来、谁能修改、如何验证、为什么这样设计。你需要能沿着文件解释整个文档系统。

一个文档系统的四个角色

01 · SOURCE

事实来源

api/openapi.yaml 描述接口契约。参数、响应结构和类型应该首先在这里成立。

02 · EXPERIENCE

读者体验

website/ 决定内容如何组织、导航、构建并最终呈现给开发者。

03 · DECISION

决策记录

docs/adr/ 解释为什么采用某种方案、放弃了什么，以及何时应重新决策。

04 · CHECK

可重复检查

website/package.json 暴露构建、类型检查和 OpenAPI 校验命令。

观察，而不是背定义

依次打开下面四个文件。每次只回答一个问题：如果这里改错了，谁会受到影响？

文件观察重点可能影响
api/openapi.yamlCollection schemaReference 的技术准确性
website/docusaurus.config.ts站点 URL、导航、断链策略发布位置与读者体验
docs/adr/0001-documentation-framework-selection.mdDecision 与 Rejected alternatives团队理解和未来换型
website/package.jsonbuild 与 validate:openapi本地与 CI 的可重复操作

你的练习

不要复制上面的词。用你自己的语言，在聊天里完成下面三句话，每句 1–3 句即可：

1. OpenAPI 文件在这个项目里的作用是…… 2. Docusaurus 站点和 OpenAPI 文件的区别是…… 3. ADR 值得保留，因为……

我会按“是否区分了事实、展示和决策”给你反馈。回答没有唯一措辞。

卡住时再看：三个提示
  • Reference 页面可能会变化，但它背后的接口契约应该有明确来源。
  • 站点框架负责发布体验，不等于它拥有全部技术事实。
  • ADR 不是会议纪要，它记录的是带取舍的决策。
本节主来源

OpenAPI Specification：了解接口描述文档的正式结构。补充阅读：Docusaurus documentation。

完成标准

你提交三条自己的解释，并能指出其中哪一项是事实来源、哪一项是发布界面、哪一项是决策证据。完成反馈后再进入 Lesson 1。

任何文件或概念不清楚，都直接问我。你的问题也是判断下一课难度的重要信号。
