Reference · Layered Decision Aid

先识别所选层次

不要先问“哪个文档框架最好”。先问：我是在选择统一门户、REST Reference 管线、某一种 SDK Reference 管线，还是质量治理方式？

一句话判断

门户统一的是读者入口；OpenAPI 或语言源码提供的是技术事实；生成器把事实变成页面；治理层检查这些页面是否仍然表达同一组能力。

四层定位

PORTAL

门户层

教程、How-to、概念、统一导航、搜索和发布体验。

REST

接口契约层

OpenAPI 描述可观察的 REST 接口，再由工具校验和渲染。

SDK

源码提取层

各语言的公开声明、类型和注释经过原生工具链生成 Reference。

GOVERNANCE

质量治理层

版本、CI、覆盖率、术语和跨 SDK 语义一致性检查。

边界提醒：真实工具可能跨层。例如 GitBook 同时提供门户和 OpenAPI 展示能力，Sphinx 也可以发布整站。本模型的作用是先分清当前决策的主要责任，不是给工具贴永久标签。

六步决策算法

  1. 命名层次：这次要解决门户、REST、某个 SDK，还是治理问题？
  2. 指出事实源：哪些信息必须先在契约、源码、类型或注释里成立？
  3. 定义输出：读者最终看到页面、交互式 Reference、IDE 提示，还是多个输出？
  4. 列硬门槛：不满足就淘汰，例如必须能在 CI 中重复构建。
  5. 查官方证据：区分核心能力、插件能力和托管产品能力；没证据就标记“待验证”。
  6. 写后果与反转条件：选择带来了什么维护责任？什么变化会让结论失效？

同层比较：门户候选

候选主要获得主要责任先验证什么
DocusaurusMarkdown/MDX、React 定制、自主管理静态站点Node/React 依赖、插件集成、版本快照维护团队能否维护前端栈；外部 Reference 如何接入
MkDocsMarkdown-first、Python 工具链、较小的上手面主题和功能常来自独立插件所需能力属于核心、主题还是插件；版本如何锁定
GitBook托管协作、网页编辑和 OpenAPI 展示依赖托管产品的工作流与能力边界本地构建、CI 控制、导入导出和权限要求

这里没有默认赢家。若公开作品集需要展示自主管理的 docs-as-code 构建，Docusaurus 或 MkDocs 的证据更直接；若非工程贡献者的网页协作是首要约束，结论可能转向 GitBook。

同层比较：REST Reference

策略获得代价与漂移风险反转条件
手写 Reference叙述和页面结构高度自由接口改动后需要人工同步；难以系统校验参数与 schema接口很小、稳定且没有可维护的契约
OpenAPI 驱动契约可校验，并可派生 Reference、Mock（按契约返回预设响应的模拟服务）、测试或客户端需要维护 spec 质量、生成配置和人工补充的任务上下文OpenAPI 并非实际接口的可信来源，或关键行为无法由其表达

同层比较：SDK Reference

策略适合什么需要警惕
通用页面手写少量稳定 API、需要大量解释性内容签名、类型、弃用信息容易与源码漂移
语言原生提取公开 surface 较大、签名随版本演进每种语言仍有独立环境与规则，不能靠一个门户生成器抹平

本课程把 Sphinx/autodoc 作为 Python 提取管线的典型例子，而不是要求它与 Docusaurus 竞争“唯一总站框架”。Java、Go 和 Node.js 分别从各自的公开声明、类型与注释出发。
